Design decisions

  • The Git tree is the only path manifest. Snapshot pins contain immutable commit/tree identity and accepted-write sequence/provenance, not file bytes or a path index.
  • Ingestion creates the pin and monotonic current pointer in the exact RepoDO transaction that commits refs. No R2 snapshot object is required for serveability.
  • Snapshot reads first prove the exact pin through RepoDO, then traverse the pinned tree and use existing pack lookup/R2 range reads with request cache disabled.
  • Reachability GC treats every retained snapshot pin as an additional want. Explicit release and qualification reset remove only the selected pin roots.

Evidence

The maintained candidate now removes ingestion bundle/manifest writes, publishes a RepoDO pin and current pointer in the accepted ref-CAS transaction, resolves snapshot bytes from pinned Git trees through pack lookup, carries pins into both immediate and durable GC closure planning, and supplies explicit release/revocation plus qualification reset behavior.

An independent Codex task review found six actionable issues: the durable queue ledger omitted pins; pack-backed reads omitted repository read leases; release still allowed legacy fallback; no injected transaction rollback test existed; cache-bypass coverage was non-distinguishing; and the end-to-end timing label was ambiguous. All six were corrected. Supplemental Fable defect discovery then found seven valid follow-ups: release incorrectly treated the historical current pointer as authority; lease refusals could masquerade as absence; probe-mode ingestion did not pin before queued projection; absent release calls could create unbounded tombstones; the GC test did not prove physical old-pack deletion; request cache setup discarded prior accounting; and snapshot read leases were mislabeled as Git fetches. Those are corrected too. One Fable claim about a missing event-probe prefix was rejected as unreachable because the event-probe enablement gate itself requires that prefix. Per supervisor correction, Fable is not the final implementation-review gate; a fresh read-only Opus/high review is pending.

The required first Opus/high implementation review did not approve the candidate as-is. It found that legacy release skipped the live-ref guard, unexpected pack failures became 404s, a generic accepted-write batch could apply one tree to several commits, invalid projection trees could create conflicting authority, obsolete staged-bundle machinery remained, and the pack-derived manifest reused the legacy version. All six were corrected: every release now checks refs first; only typed path absence is 404 and other pack/manifest failures are retryable 503; pin input is bound to exactly one accepted commit; bad tree identity returns a non-mutating tagged result; unused staging/source-fast-path code and its test are gone; and the pack-derived manifest is version 2.

Three subsequent fresh Opus/high passes found and drove correction of further bounded issues: manifest path validation and transient error classification, eliminating the remaining production queue bundle-copy path, invalid release configuration, structured read logging, shared limit/type definitions, deleting/capacity status distinctions, lease-release fault isolation, bounded no-content inspection, tagged release outcomes, release warnings and unreadable legacy-manifest handling, and ensuring a stale disposable pin cannot veto an otherwise valid ref CAS. The fourth pass narrowed the gate to three final corrections: store only compact commit OIDs in durable GC operation snapshots, preserve the queue request's limiter/private-cache memo when switching from the control-plane repository ID to the RepoDO name, and apply the ordinary cold-cache/pack-count safeguards to pack-backed snapshot benchmarks. Those corrections and distinguishing tests are now present. A fresh Opus/high review approved the candidate but also identified a credible queue/GC race: the queue released its read fence after object inspection but before installing the pin. Although reported as non-blocking, it directly touched snapshot immutability, so the candidate now keeps the fence through the projection RPC and tests deletion safety at that exact boundary. A second fresh Opus/high pass approved that correction but exposed the complementary root-set race: GC publication fenced refs and packs but not a pin added after its root snapshot. The candidate now snapshots pin OIDs and a monotonic pin version atomically, checks that version at every GC publication path, and uses a dedicated snapshot-projection lease to prevent catalog publication between successful inspection and pin installation without blocking ordinary readers. A test proves both the active-projection and changed-pin fences. A final fresh Opus/high pass approved that design but identified that an expired fixed-duration projection lease was not revalidated inside the pin transaction, the event-probe projection consumer did not hold the new lease, and coordinated receives did not advance the exact pin version they created. The authority now requires a live matching projection token before creating a new pin, both consumers hold and pass it, expired tokens retry without pinning, and coordinated receive accounting advances only from the pin version observed before its own transaction work to the version observed afterward. New tests distinguish expiry rejection and a pinning receive that still permits coordinated GC publication. That confirmation then found one remaining cleanup bug: a pin-version change between durable GC begin and snapshot registration rejected progress but left the newly acquired compact lease and claim live for their long TTLs. The registration path now handles the tagged result directly, aborts the just-acquired lease, yields to clear its claim, and returns a normal retry. A test injects a real pin in that exact RPC gap and proves immediate lease/claim cleanup. Clean final Opus/high confirmation approved the complete candidate with no issues found.
